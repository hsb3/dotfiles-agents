VOL. 01API SERVERSPART I — LAYERING
Tutoring session — Henry · v0.7

An API server is a containment strategy, not a folder layout.

Every layer in a well-built API exists to absorb a specific kind of change so the others don't have to. Names like "route", "service", "repository" only make sense once you see the pressures they're each defending against.

The driving principle — each layer absorbs one kind of change. Routes absorb HTTP. Services absorb business rules. Repositories absorb storage. Schemas absorb the contract. Violate this and changes ripple.

Derivation

Four pressures produce four layers.

Don't memorize the layers. Derive them. Each one is the answer to a real failure mode you'll hit if you skip it.

PRESSURE 01
The wire is hostile and untyped.
Bytes arrive over HTTP. Headers might lie, JSON might be malformed, fields might be missing. Someone has to parse, validate, authenticate, and reject before any real work happens.
→ produces the route + schema layers
PRESSURE 02
Logic shouldn't know it's HTTP.
If your business function takes a Request object or raises HTTPException, you can't reuse it from a worker, CLI, or test without faking HTTP. That's a leak.
→ produces the service layer
PRESSURE 03
Storage shouldn't be sprinkled.
If every service writes raw SQL, you can't swap stores, add caching, mock for tests, or audit access in one place. The ORM leaks into your business logic.
→ produces the repository layer
PRESSURE 04
Wire shape ≠ storage shape.
Stored rows have audit columns, internal IDs, soft-delete flags clients shouldn't see. Conflating them couples your API contract to your migrations forever.
→ produces schemas vs. models separation
Mnemonic

Two contracts. Two bindings. One brain.

Now that you've seen the five layers and the pressures that produce them, the structure compresses. Each surface (wire and storage) gets one contract defining its shape and one binding moving data across it. Services sit between, blind to both surfaces.

Routes and repositories are mirror images: same pattern, different surface. A route translates between HTTP and a service call; a repository translates between a service call and storage. Both are bindings.

routes  ·  wire binding  ·  endpoint.method ↦ (schema_in, service, schema_out)
schemas  ·  wire contract  ·  shape on the HTTP surface
services  ·  brain  ·  business rules; compose repos & other services; no HTTP, no SQL
repositories  ·  storage binding  ·  query ↦ (model_in, storage_engine, model_out)
models  ·  storage contract  ·  shape on the storage surface

Concrete shape

One endpoint, five layers, in FastAPI.

GET /users/{id} where soft-deleted users return 404. Notice each layer mentions only what it's allowed to know.

# schemas/user.py — wire shape
class UserRead(BaseModel):
    id: int
    email: str

# models/user.py — storage shape (separate concern)
class User(Base): __tablename__ = "users" ...

# repositories/user.py — storage operations
def get_active_by_id(db, user_id) -> User | None:
    return db.query(User).filter(
        User.id == user_id, User.deleted_at.is_(None)
    ).first()

# services/user.py — business rules, no HTTP, no SQL
class UserNotFound(Exception): ...

def fetch_user(db, user_id) -> User:
    user = user_repo.get_active_by_id(db, user_id)
    if user is None: raise UserNotFound(user_id)
    return user

# routes/user.py — HTTP only
@router.get("/users/{user_id}", response_model=UserRead)
def get_user(user_id: int, db=Depends(get_db)):
    try:
        return user_service.fetch_user(db, user_id)
    except UserNotFound:
        raise HTTPException(404, "User not found")
Per-Layer Guidance

Three questions for every line you write.

For each layer, ask: what does it know (allowed dependencies), what does it return (output and error shape), and what's the smell that says another layer's concern has leaked in. Same lens, five answers. Order below — services first, since the rest are largely defined by what services can and can't touch.

services
brain · pure logic
Knows
  • domain types & data classes
  • repositories
  • other services (composition)
  • domain exceptions it defines
Returns
  • domain objects (or primitives)
  • raises a domain exception (UserNotFound, InsufficientFunds)
  • never HTTPException
  • never wire-shaped dicts
Smells
  • from fastapi …
  • raw SQL or ORM query construction
  • request: Request as a parameter
  • hardcoded HTTP status codes
KeyMust be callable from a CLI script, a Celery worker, or a unit test with zero HTTP scaffolding. If it isn't, you've leaked.
routes
wire binding · http only
Knows
  • HTTP — status codes, headers, cookies
  • schemas (input + output)
  • services (calls them)
  • auth dependencies
Returns
  • a response_model instance
  • or raises HTTPException after translating a domain exception
  • status codes are explicit
Smells
  • if-branches over domain conditions
  • direct DB queries in a route
  • building dicts by hand instead of returning a schema
  • orchestrating multiple service calls — that's a service
  • handler longer than ~30 lines
KeyEvery route should look the same: validate via schema → call service → translate domain exception to HTTP → return. Boring is correct.
schemas
wire contract · shape on http
Knows
  • Pydantic / validation library only
  • field types, formats, length, regex
  • serializers / aliases for the wire
Returns
  • typed Python objects from JSON in
  • JSON-serializable dicts out
  • that's it — no behavior
Smells
  • a single schema doubling as ORM model
  • schemas importing models or hitting the DB
  • validators that need DB state ("email must be unique")
  • one bloated User for create/read/update
KeyInput ≠ output ≠ patch. Expect at least three per resource: UserCreate, UserRead, UserUpdate. Reusing one is a tell.
repositories
storage binding · storage ↔ service
Knows
  • ORM / DB driver / Supabase client
  • models (returns them)
  • query construction
  • session/connection (taken as parameter)
Returns
  • Model, None, or list[Model]
  • never raises domain exceptions — "found nothing" is a return value, not an error
  • never returns dicts or schemas
Smells
  • raising UserNotFound or HTTPException
  • methods named after business intent (approve_user) vs storage intent (update_status)
  • if-branches over business state
  • functions that span multiple aggregates
KeyOne repository per aggregate root — the entry point of a tightly-coupled cluster of entities (e.g., Order owns its OrderLines; you load and save them as a unit). Transactions span repositories — but the service opens, commits, and rolls back. Repos just execute inside the session they're handed.
models
storage contract · shape on storage
Knows
  • tables, columns, indices, constraints
  • relationships
  • audit fields (created_at, updated_at, deleted_at)
Returns
  • itself — passive shape
  • no behavior, no methods beyond what the ORM requires
Smells
  • business methods (user.deactivate()) — services do that
  • computed properties that hit the DB on access
  • validation logic — that's schema territory
  • models referenced directly in routes
KeyModels are passive shapes. Active-Record patterns (Django, Rails — where the model itself has .save(), validations, and business methods) blur every other layer; keep models stupid and put behavior in services.
Each layer holds a different definition of the same fact.
A "deleted" user, by layer:
model
a row with deleted_at set to a timestamp
repository
a query that filters that row out
service
an entity that doesn't exist for business purposes
route
a 404 response
schema
an absence from the response payload
Rejection & Rework

The system is a constrained transformation. Rejection is part of the contract.

An API takes information meeting some preconditions X and returns refined information meeting some postconditions Y. Setting aside queueing, parallelism, and replication — the most under-discussed part of any production system is how it refuses work and tells the client what to fix. Treat that as first-class design, not afterthought error handling.

PRINCIPLE 01
Shift left.
The cheapest rejection is the earliest one. A schema rejection costs nothing — no DB hits, no logic. A service rejection costs reads. A storage rejection wastes the whole transaction. Move every check toward the wire that you safely can.
PRINCIPLE 02
Two flavors of "no".
Structural — the payload is malformed (4xx, client fixes shape). Semantic — the payload is well-formed but breaks rules (4xx, client may need external action: top up, contact support, retry later). Status codes encode which.
PRINCIPLE 03
Errors are part of the schema.
Define an ErrorResponse with stable codes: {code, message, field?, hint?}. Codes are part of the API contract. "validation_failed" is useless; "insufficient_funds" lets clients build flows around it.
Worked Example

POST /transfers — moving money between two accounts.

One operation, all five layers, every rejection mode. Pseudocode below is language-agnostic — read for shape, not syntax.

  1. Define the contract. URL + method + request schema + response schema. The shape of success.
  2. Enumerate rejection cases. Every way it can fail, mapped to HTTP status and stable error code. The shape of failure.
  3. Design persistence. Models, indices, constraints. What needs to survive a restart.
  4. Sketch repository signatures. What storage operations the service will need — names and types only, no implementation.
  5. Implement the service. Business logic plus the rejection cascade from step 2.
  6. Implement the route. Pure translation: domain exception → HTTP status + ErrorResponse.
  7. Implement repositories last. Least likely to drive design decisions; easiest to swap later.

The ordering matters: by the time you reach step 5, every design decision is made. You're not writing logic and deciding what should happen — only writing logic to enact decisions already taken. That's the value of outside-in.

STEP 01 Contract — schemas // wire-side shapes, what the client sees 
schema TransferRequest:
  source_account_id      : UUID
  destination_account_id : UUID
  amount                 : Decimal, > 0, <= 10_000_000
  currency               : String, matches ISO_4217   # "USD", "EUR", ...
  idempotency_key        : UUID                       # client-generated, prevents replay
  note                   : String?, length <= 500

schema TransferResponse:
  transfer_id            : UUID
  status                 : Enum["completed", "pending"]
  source_account_id      : UUID
  destination_account_id : UUID
  amount                 : Decimal
  currency               : String
  created_at             : Timestamp

schema ErrorResponse:
  code    : String     # stable, machine-readable: "insufficient_funds"
  message : String     # human-readable summary
  field   : String?    # which input field, if applicable
  hint    : String?    # how the client might recover
STEP 02 Rejection map // design the failure surface BEFORE writing logic 
# enumerate every rejection, where it fires, the http status + code returned

  layer     | failure                          | status | code
  ----------|----------------------------------|--------|-----------------------------
  schema    | amount <= 0 or > 10M             |  422   | invalid_amount
  schema    | bad UUID, bad currency code      |  422   | invalid_field
  route     | no/invalid bearer token (auth)   |  401   | unauthorized
  service   | source or dest account missing   |  404   | account_not_found
  service   | source not owned by caller       |  403   | forbidden
  service   | source frozen / dest closed      |  409   | account_unavailable
  service   | source.currency != dest.currency |  422   | currency_mismatch
  service   | source.balance < amount          |  422   | insufficient_funds
  service   | daily limit exceeded             |  429   | daily_limit_exceeded
  repo      | idempotency_key collision (race) |  409   | duplicate_request
  storage   | deadlock / connection lost       |  503   | service_unavailable
STEP 03 Persistence — models // shape on the storage surface 
model Account:
  id          : UUID, primary_key
  owner_id    : UUID, foreign_key(User)
  balance     : Decimal, default 0
  currency    : String
  status      : Enum["active", "frozen", "closed"]
  created_at, updated_at

model Transfer:
  id                     : UUID, primary_key
  source_account_id      : UUID, foreign_key(Account)
  destination_account_id : UUID, foreign_key(Account)
  amount                 : Decimal
  currency               : String
  idempotency_key        : UUID, unique     # DB enforces no replay
  status                 : Enum["completed", "pending", "failed"]
  created_at             : Timestamp
STEP 04 Repository signatures // names & types only — no impl yet 
repository account_repo:
  get_by_id(session, account_id)              -> Account | None
  update_balance(session, account_id, amount) -> Account

repository transfer_repo:
  get_by_idempotency_key(session, key)        -> Transfer | None
  sum_for_account_today(session, account_id)  -> Decimal
  insert(session, transfer)                   -> Transfer

# note: repos return models or None — never raise domain exceptions.
# they take a session — they do NOT open or commit transactions.
STEP 05 Brain — service + domain exceptions // every check from step 2's rejection map lives here 
# domain exceptions — defined alongside the service that raises them
exception AccountNotFound(account_id)
exception UnauthorizedAccess(account_id)
exception AccountUnavailable(account_id, reason)
exception CurrencyMismatch(source_ccy, dest_ccy)
exception InsufficientFunds(account_id, requested, available)
exception DailyLimitExceeded(account_id, limit)

service transfer_service.create(session, request, user) -> Transfer:

  # [1] idempotency — replay safety, costs one read
  existing = transfer_repo.get_by_idempotency_key(session, request.idempotency_key)
  if existing is not None:
    return existing                          # safe replay, same response

  # [2] resolve entities — earliest cheap rejections first
  source = account_repo.get_by_id(session, request.source_account_id)
  if source is None:
    raise AccountNotFound(request.source_account_id)

  dest = account_repo.get_by_id(session, request.destination_account_id)
  if dest is None:
    raise AccountNotFound(request.destination_account_id)

  # [3] authorization & state
  if source.owner_id != user.id:
    raise UnauthorizedAccess(source.id)
  if source.status == "frozen":
    raise AccountUnavailable(source.id, "frozen")
  if dest.status == "closed":
    raise AccountUnavailable(dest.id, "closed")

  # [4] business rules
  if source.currency != dest.currency:
    raise CurrencyMismatch(source.currency, dest.currency)
  if source.balance < request.amount:
    raise InsufficientFunds(source.id, request.amount, source.balance)

  daily_so_far = transfer_repo.sum_for_account_today(session, source.id)
  if daily_so_far + request.amount > DAILY_LIMIT:
    raise DailyLimitExceeded(source.id, DAILY_LIMIT)

  # [5] execute atomically — service owns the transaction boundary
  with session.transaction():
    account_repo.update_balance(session, source.id, source.balance - request.amount)
    account_repo.update_balance(session, dest.id,   dest.balance   + request.amount)
    transfer = transfer_repo.insert(session, Transfer(
      source_account_id      = source.id,
      destination_account_id = dest.id,
      amount                 = request.amount,
      currency               = source.currency,
      idempotency_key        = request.idempotency_key,
      status                 = "completed",
    ))

  return transfer
STEP 06 Translation — route // HTTP in, HTTP out, no business logic 
route POST /transfers:
  request : TransferRequest            # schema validates → 422 on failure
  auth    : Bearer token -> user       # missing/invalid → 401

  try:
    transfer = transfer_service.create(session, request, user)
    return 201, TransferResponse(transfer)

  except AccountNotFound as e:
    return 404, ErrorResponse(
      code="account_not_found",
      message="Account does not exist",
      field="source_account_id" if e.account_id == request.source_account_id else "destination_account_id",
    )

  except UnauthorizedAccess:
    return 403, ErrorResponse(code="forbidden", message="Not your account")

  except AccountUnavailable as e:
    return 409, ErrorResponse(
      code="account_unavailable",
      message="Account is " + e.reason,
      hint="Contact support to reactivate",
    )

  except CurrencyMismatch as e:
    return 422, ErrorResponse(
      code="currency_mismatch",
      message="Source and destination currencies differ",
      hint="Use a foreign-exchange transfer endpoint",
    )

  except InsufficientFunds as e:
    return 422, ErrorResponse(
      code="insufficient_funds",
      message="Balance too low for this transfer",
      hint="Available: " + e.available,
    )

  except DailyLimitExceeded:
    return 429, ErrorResponse(
      code="daily_limit_exceeded",
      message="You have reached today's transfer limit",
      hint="Try again after midnight UTC",
    )

# Note: in real FastAPI you'd register these as global exception handlers
# once, not in every route. Shown inline here to make the mapping explicit.

Notice the route is mechanical. Every except branch is bookkeeping — translating a domain fact into an HTTP fact. No decision is being made. Every real decision happened in the service. That's the test of whether your layering is working: the route should be boring.

Don't cargo-cult this. For a 5-endpoint internal API, all four layers is overkill — collapse service + repository into the route and you'll be fine. The pressures only start biting around ~15+ endpoints, multiple consumers, or non-trivial business rules. The skill is recognizing when each layer starts paying for itself, not always reaching for all four.

Appendix · Beyond this Primer

What this document doesn't cover.

This is a primer on the structural skeleton — five layers, contracts and bindings, rejection design, outside-in sequencing. A production API depends on a much wider set of concerns. Below: what was deliberately set aside, organized by when you'll need it. Where a canonical reference exists and aligns with this primer's framing, it's linked; otherwise the topic is named so you can chase it further.

Section A
Cross-cutting concerns.
// live at every layer · need a single home so they don't smear across all of them
Authentication & authorization // who are you, and what may you touch
Authentication identifies the caller (route layer, via auth dependency). Authorization checks whether that caller may touch a specific resource (service layer — the rule depends on business state). Different layers, different concerns; conflating them is the most common auth mistake.
canonical → OWASP API Security Top 10  ·  (no single doc covers session vs JWT vs OAuth — choose by deployment)
Logging & observability // what happened, where, how long
Structured logs, distributed traces, and metrics that thread through every layer. The hard part isn't emitting events — it's correlation. A request_id (or trace_id) that follows a request from route through service through repository, and into downstream services, makes the difference between observability and noise.
canonical → OpenTelemetry  ·  12-Factor: Logs
Configuration & secrets // everything that changes between environments
DB URLs, API keys, feature flags, region-specific values. Lives in environment variables or a secret store, never in code, never in version control. Read once at startup and injected via dependencies — never re-read mid-request.
canonical → 12-Factor: Config
Error response format // the JSON shape of every 4xx and 5xx
A consistent envelope across the entire API — not invented per-endpoint. The primer's ErrorResponse sketch (code, message, field, hint) is good; better is to adopt the IETF standard so clients can parse errors without per-API special cases.
canonical → RFC 9457 — Problem Details for HTTP APIs
Request context propagation // user, tenant, locale flowing through layers
Information that every layer might need but nobody owns — current user, tenant ID, request ID, locale. Threading these as parameters everywhere is noise. Most frameworks provide a context object or dependency-injection mechanism; pick one and standardize.
(framework-specific — FastAPI dependencies, Express middleware, etc.)
Section B
Production realities.
// the difference between "works on my machine" and "serves real clients"
API versioning // breaking changes, but managed
Once external clients depend on you, breaking changes require a version bump. Most teams use URL prefixes (/v1/) or accept headers. The mechanism matters less than the discipline: enumerate your breaking-change rules, communicate deprecation timelines, never silently change a contract.
(no single canonical doc — Stripe's versioning model and Microsoft's REST guidelines are the most-cited references)
Pagination & filtering // every list endpoint, no exceptions
Never return an unbounded list. Pick offset-based (simple, breaks under writes) or cursor-based (complex, stable) and apply consistently. Filtering syntax is similarly a one-time design decision; commit early.
(no canonical doc; vendor-specific — GitHub, Stripe, and JSON:API are reasonable models)
Idempotency at scale // safe retries for mutations
Any POST that mutates external state (charges, transfers, sends, provisions) should accept an Idempotency-Key header. The worked example sketches this; production-grade implementation handles partial failures, replay windows, and concurrent retries — non-trivial.
canonical → Stripe — Idempotent Requests  ·  Brandur Leach — Implementing Idempotency Keys in Postgres
Health checks & readiness // can the orchestrator route to me?
/healthz = is the process alive? /readyz = are my dependencies (DB, cache, downstream APIs) reachable, and am I prepared to serve? Required by every modern orchestrator. Get this wrong and rolling deploys fail mysteriously.
(orchestrator-specific — Kubernetes liveness/readiness probes are the de-facto pattern)
Rate limiting & quotas // defending the service from itself
Lives above the route layer — usually a gateway, reverse proxy, or middleware. Per-IP, per-API-key, per-user, per-endpoint. Defends both your service and your downstream dependencies. Almost always required before opening to untrusted callers.
(no settled canonical; IETF draft on RateLimit headers is moving in that direction)
OpenAPI / contract publication // your schemas, generated
Your request and response schemas already define the contract. Publishing them as OpenAPI lets consumers generate types, mocks, tests, and documentation. FastAPI does this for free; capture and version the artifact alongside your code.
canonical → OpenAPI Specification
Section C
Testing the layers.
// the layering's primary payoff

Each layer is independently testable, and that's the point. Services are pure — mock the repos, run thousands of unit tests in milliseconds, exercise the rejection cascade with no DB. Repositories need real storage — slower integration tests against a real database (Postgres in a container, or Supabase test project). Routes need an HTTP client — fewer end-to-end tests, mostly verifying status codes and the schema-to-domain wiring. Skew your test count toward services; that's where the logic lives.

canonical → Martin Fowler — The Test Pyramid
Section D
Read patterns are different from write patterns.
// often-skipped design decisions

List endpoints have concerns that mutation endpoints don't: pagination, filtering, sorting, projection (which fields to return), and the N+1 problem (loading related entities in a loop). At scale, the read side and write side diverge enough that some teams split them entirely — the CQRS pattern. Most APIs don't need that, but knowing it exists shapes how you design the read side: optimize joins for common queries, accept that the response shape may diverge from the model shape further than on the write side, and consider caching at the repository or service boundary.

(no single canonical doc — Martin Fowler on CQRS is the standard reference if you want to go deep)
Section E
Out of scope for this primer, but real.
// you'll meet these eventually
  • Streaming responses (Server-Sent Events, WebSockets) — when a single request/response cycle isn't enough
  • Webhooks — when your service is the client, calling someone else's API on events
  • Background jobs & async services — when work outlives a single request (queues, workers, schedulers)
  • File uploads — multipart bodies, S3 presigned URLs, virus scanning, size limits
  • Multi-tenancy — row-level vs schema-level vs database-level isolation
  • Distributed transactions — sagas, outbox patterns, eventual consistency
  • Event sourcing & CQRS — when the write side and read side fully separate

When a new concern arrives, ask: which layer absorbs it? If the answer is "all of them, a little," you've found a cross-cutting concern — place it once (middleware, dependency injection, context object) and let the layers ignore it. The framing in this primer applies to every concern not yet covered.
