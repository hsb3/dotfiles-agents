# SOP feedback

## Unclear, wrong or missing

- **Step 3 block, shell portability.** Factoring the shared ghost flags into a variable (`D="--parent … --draft v1"; groma draft component "X" $D …`) fails under zsh, the macOS default shell, because zsh does not word-split unquoted parameters: every call failed with `unknown option '--parent agent-harness-cli --draft v1 …'`. A shell function wrapping `groma draft component` worked. A note in the block that the flags must be repeated (or wrapped in a function) would save a round trip.
- **Step 3, a store whose natural ID equals a planned component's.** The spec names the ledger both as a data store (`results.jsonl`) and as the thing a `ledger.ts` component writes. Declaring the store as `Ledger` took the ID `ledger`, which the ghost (and the scanner's file-stem match) needs. Nothing in the skill warns that store and component IDs share one namespace; I renamed the store with `groma edit ledger --id results-ledger` before drafting the ghost. Suggest: "name data stores so their kebab ID differs from every planned file stem".
- **Step 4, task dependencies vs. shared types.** Several adapters implement one interface owned by a registry component. The SOP's "one task per independently reviewable slice" plus `--dep` leaves open where a shared type goes when the type's owner is built in a later task than its first user; I folded the registry and the first adapter into one task. A sentence on that (build the interface owner first, or together with its first implementer) would help.
- **Scaffold vs. spec.** The init scaffold had `typescript` under `peerDependencies`, while the spec's Stack section wants it as an exact devDependency. The skills do not say whether to treat scaffold drift as in scope for the first task; I fixed it in TASK-1 and noted it there.
- **Step 5, overviews of components a task changes indirectly.** "Keep touched overviews true" reads as "the components whose files the task edited". In TASK-11 a change in `trial.ts` changed what `check.py` runs with, which the `checks` overview (an untouched file) described; it stayed wrong until the close review caught it. Suggest: after the accepts, also re-read the overviews of the components the task's changed code calls into, not only the files it edited.
- **Step 5, recording files.** The PostToolUse hook records file-tool edits, but the `.groma/` records that `groma scan` rewrites as a side effect (e.g. a caller's component doc after a new derived row) are easy to miss when reading command output across many commands. Setting the list from git before finishing (the SOP's one-liner, which I kept as a small script) was the only reliable way; I'd make that the primary instruction rather than the fallback.
- **`groma view <file>` scope.** For an adapter whose accepted relations go to a declared store and an external, `groma view src/opencode.ts` listed only the component-to-component rows, so it looked as if the accepts had not landed; `groma view <container> --plain` showed them. A note that the file view shows component rows only would avoid the double-check.
- **Step 6 ordering.** The milestone completes by itself when the last task is Done, so `backlog milestone list --plain` (without `--show-completed`) shows nothing right before the close; the skill says so, but the session-start hook's "no release is open" wording at that moment could be read as "nothing to close". The close itself (draft removal, strict lint, quality record, render) went through without a hitch.
- **Stack notes, HOME and shims, beyond tests.** The stack notes warn that a version-manager shim on `PATH` fails when a test sets `HOME`. The same applies to product code that runs a child with an isolated `HOME`: running `check.py` under the per-run home broke a mise `python3` shim (`Config files … are not trusted`). Worth one line in the stack notes for tools that sandbox their children.

## Worked well

- The first scan was instant and the `--id` rename of the scanned container kept everything (`replaced:` line made it obvious nothing was lost).
- `groma draft relation` for every planned link, including to externals and declared stores by ID, made the planned map complete before any code existed; `groma lint` was clean straight after planning.
- The PostToolUse hook recording file-tool edits on the In Progress task removes most of the `--modified-file` bookkeeping; a small `git diff`-based script covers shell-written files before finishing.
- `groma lint`'s duplicate-logic gate caught a real copy (`isDir` in `campaign.ts` and `cases.ts`) and forced a cleaner helper, at no cost elsewhere.
- Derived rows (`Calls imported function`, `Invokes supplied callbacks`) were a reliable checklist of links the design had missed: every one led to an authored relation with a real description (adapter helpers, output callbacks, the smoke log).
- Planning flows only once their relationships existed (step 5) meant every flow was accepted on the first try; the three flows read in execution order with no placeholder steps.
- `groma-quality.sh render` and `groma lint --strict` at close gave an objective finished-state check in two commands.
