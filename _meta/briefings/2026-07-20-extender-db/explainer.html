Extender-DB: the catalog and its standards, both as data

This is a walkthrough of what was built on the feat/extender-db branch: a PocketBase database that holds every agent extender this repository distributes or curates — skills, agent personas, hooks, and externals — joined to the mental models we compose and evaluate them by. Every number on this page was queried live from the database it describes.

Act 1 · Why this exists

Curating a growing catalog by re-reading files doesn't scale

The repository already had strong distribution machinery — a roster manifest, drift guards, a marketplace generator. What it lacked was an analysis substrate: a way to ask "which skills lack worked examples", "what frontmatter keys do we use that no spec defines", or "how well does the catalog conform to Anthropic's authoring guidance" without opening twenty-three folders.

The second idea is the one that shapes the design: the standards themselves are data. If Anthropic promotes a set of skill archetypes, that is a record with a citation — something to evaluate the catalog against and compose new skills by, not folklore. Internal taxonomies get the same treatment, marked as internal and candidate, so competing mental models can be compared against the same corpus and superseded without losing history.

The repo stays the source of truth. The database is a rebuildable projection — content never flows back from it; a finding becomes a fix in primitives-core/, then a re-ingest.

Act 2 · The data model

Two halves, joined by assessments

Seven collections. The inventory side records what each extender is; the doctrine side records the frameworks we judge by. The join is assessments: one verdict per extender × framework-element × assessor, which makes "how conformant are we" and "what shape is the catalog" both one-query questions.

Act 3 · How it was populated

A small crew, with adversarial review that earned its keep

Mechanical facts come from ingest.py (idempotent, stdlib-only, proven by zero-record re-runs). Judgment came from a fan-out: six judge agents each read a batch of skills and returned structured JSON verdicts with evidence quotes — they never held database credentials. Two reviewers blind-re-derived an eight-skill sample. The session compared, adjudicated, and loaded.

6 judges (sonnet)

All 23 skills → archetype + 9 section verdicts each, with evidence. Output: JSON files, not DB writes.

2 blind reviewers (opus)

Re-derived 8 stratified skills without seeing the judges' answers. Agreement: 6/8 primaries; 15 of 16 section disagreements were adjacent (partial-boundary calls), one hard flip.

1 builder (sonnet)

Extended the ingest to hooks + externals, proving its work on a throwaway PocketBase instance — the live DB was never its to touch.

The session (gates)

Adjudicated 3 disputes from sources, ran every gate on the live DB, and caught the one real escape: the builder had patched a schema gap (kind: plugin) only on its throwaway instance. Fixed durably in schema.py.

The three adjudications: handoff → workflow-procedure (body is dominated by protocol; the artifact skeleton is subordinate), private-fork → domain-expertise (the SKILL.md body is doctrine; the procedures live in references/), and private-fork's integration-partners → absent (its table lists its own files, not sibling components). Full log in _structure/OPEN-ITEMS.md.

EDB-9  obsidian-cli's "Additional Resources" cites five files that don't exist on disk (query-commands.md, plugin-commands.md, developer-commands.md, batch-operations.sh…). Found independently by a judge and a blind reviewer — confirmed, actionable.

EDB-3  Two skills exceed the ≤500-line SKILL.md guideline: diagrams (653 lines) and obsidian-cli (753 lines). Candidate fix: push depth into references/.

EDB-4  Three frontmatter keys no spec defines: skill metadata (×2), skill version (×2), agent memory (×1). Adopt into an internal spec or remove.

Decisions in the owner's court: action EDB-9 (which would also serve as the update-path proof), fold the reviewers' calibration notes into a criteria v2 before any second judging pass, build the W4 report surface (PocketBase view collections + report.py), and — once the gate is full — decide where this lives: stay in _meta/, graduate to scripts/ with a make lane, or its own repo.

Operating it: _meta/extender-db/serve.sh starts the server (admin UI at 127.0.0.1:8090/_/); schema.py and ingest.py rebuild everything from the tree; credentials live in the untracked _meta/operations/extender-db.env.
