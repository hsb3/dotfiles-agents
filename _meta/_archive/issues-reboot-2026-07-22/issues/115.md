Build `skill-bundle`: a second, primitive-level distribution surface for catalog-qualified standalone skills. It does not change the two workflow bundles or the fixed target in decision 0007.

## Deliverables

- A versioned catalog declaring a skill's canonical source, provenance, standalone eligibility, client compatibility, and dependency declaration.
- Claude Code: derive one-skill plugin wrappers and marketplace entries from the catalog, allowing `/plugin install <skill>@dotfiles-agents` without installing `project-workflow` or `repo-standards`.
- OpenCode: a documented `install-skill <name>` interface that installs exactly one compatible skill to an OpenCode-supported directory (default global `~/.agents/skills/<skill>/`; project-local explicit).
- A small, explicitly selected initial skill set, limited to self-authored `primitives-core` skills that require no hooks, agents, MCP servers, shared scripts, or sibling skills.
- README covering bundle-vs-standalone choice and an install example per client.

## Acceptance criteria

- [ ] Canonical skill bodies exist once only; generated client adapters do not create hand-maintained skill copies.
- [ ] Every listed entry has catalog-backed eligibility, source/provenance, client compatibility, and an explicit dependency declaration.
- [ ] Generated Claude wrappers expose only their named skill; the existing marketplace installs one such skill successfully.
- [ ] OpenCode installer installs one named compatible skill to a supplied test directory, rejects unknown/ineligible/incompatible names clearly, and documents update/uninstall behavior.
- [ ] Smoke tests prove Claude install and OpenCode discovery without writing to real global skill directories.
- [ ] Catalog/source and generated-artifact drift checks run in CI.
- [ ] `make build` and existing drift guards remain green.

## Non-goals

- No dependency resolver or installation of hooks, agents, MCP servers, or shared scripts.
- No wholesale third-party skill catalog.
- No change to the two shipping workflow bundles.

## Sequencing

Build after #111: it targets the rewrite's cleaned `primitives-core`, final marketplace manifest, and provenance boundary. Design may start earlier; do not edit the marketplace manifest while #112/#113 hold the serialized surface.
