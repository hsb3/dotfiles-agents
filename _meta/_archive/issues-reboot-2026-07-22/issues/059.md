## Body

> **Origin:** the #24 loadability smoke's first run. The opencode agent transform passed CC frontmatter through verbatim and opencode 1.17 rejected it at load — the interim fix (PR for #24) DROPS the `tools:` key, which loses permission narrowing. Owner-ruled 2026-07-02: drop for now, redesign the baseline as the real fix.

## Problem

`primitives-core/` uses **Claude Code's formats as the base format**, and `translate.py` transforms CC → each target. That works for prose (skills) but breaks down wherever vendors have *semantically different* config surfaces:

- **`tools:`** — CC uses an allowlist (`tools: Read, Grep`); opencode uses a per-tool boolean map that toggles against defaults, so a converted list loads but does not narrow. Currently dropped in the opencode transform (agents get default toolset — widening documented in the transform docstring).
- **env interpolation** — our mcp fragments carry `"${VAR}"` (CC style); opencode does NOT substitute `${VAR}` (its form is `{env:VAR}`), so generated opencode `environment` values are passed literally. Latent bug, same family.
- **frontmatter dialects** — CC parses agent frontmatter leniently; opencode strictly (two source agents with raw multiline descriptions loaded in CC but were silently dropped by opencode until normalized).

## Direction (owner-ruled)

Develop an **agnostic base format** for primitives plus an explicit **cross-vendor mapping layer** (tool ids, permission semantics, env interpolation, frontmatter dialect), instead of CC-as-baseline.

**Research first:** someone has likely already solved cross-CLI agent/config portability in an open-source tool — survey the space (agent format converters, multi-tool dotfile managers for coding agents, e.g. the ecosystems around AGENTS.md, opencode plugins, aider/goose/codex config layers) before inventing a schema.

## Deliverables

- A — survey of prior art for cross-vendor agent/tool/config mapping; recommendation memo (adopt / adapt / build).
- B — proposed base-format spec for the primitive types we translate (agents first; skills are already near-portable), with the vendor mapping tables (tool ids, permission semantics, env interpolation).
- C — migration plan for `primitives-core/` + `translate.py` (per-type, incremental; drift guards keep working throughout).

## Acceptance criteria

- [ ] The `tools:` narrowing intent survives translation to opencode (or the spec explicitly records it as unsupported per vendor, surfaced in the build report — no silent widening).
- [ ] mcp env interpolation renders in each vendor's own syntax.
- [ ] `make smoke` green across the board after migration.

## Dependencies & gates

- Depends on: #24 (the smoke that detects these regressions) — merged first.
- `make ci` aggregate: fires on any translate.py/roster change.

## Out of scope

- Runtime shims or wrappers — this stays a static translation service.
