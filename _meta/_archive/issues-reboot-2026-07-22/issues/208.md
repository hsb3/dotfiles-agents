## Body

Follow-up from #151 Part B (closed via PR #206). The issue's Part B asked whether a distributable skill should operationalize creating this repo's own work product (scaffold a conformant `primitives-core/<type>/<id>/` layout + roster entry, passing drift guards and tests).

PR #206's investigation found this can't ship as a **rostered/distributed** skill: `make ci`'s identity-neutrality lint (`check_identity.py`) forbids hardcoded repo/org/issue references in any shipped `primitives-core/{skills,agents,hooks}` body, and this task is inherently repo-specific (it needs to know about `primitives-core.yaml`, this repo's roster schema, this repo's `make build`/`make ci` invariants by name). Extending `mise-en-place-scaffold` or `repo-meta-structure` (generic, cross-repo standards) would pollute them with one repo's specifics.

The contribution loop itself is now served by `.github/CONTRIBUTING.md` (#151 Part A, exempt from the identity lint). This issue is only the optional next step: a **project-local** skill at `.claude/skills/author-primitive/` (never rostered, never distributed) that scaffolds a new primitive to this repo's standard. Low priority — CONTRIBUTING.md already gets a newcomer to a working primitive by hand.
