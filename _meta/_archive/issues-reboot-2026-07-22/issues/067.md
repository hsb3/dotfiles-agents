## Body

Found on the fleet-dashboard test-bed run (2026-07-03, plugin 0.2.1) — the first scaffold onto a repo with NO existing workflows, so all three GH workflow templates landed verbatim as CREATE (raptorgpt/workbench had their own workflows, which surfaced as CONFLICT rows instead, hiding this).

## Problem

- `assets/.github/workflows/ci.yml` runs `make ci` and sets up **Python 3.13**. A repo whose Makefile has no `ci` target (fleet-dashboard) gets a red required-check on the very first push; a non-Python repo gets the wrong toolchain. The template header says "adapt" but nothing in the scaffold output says adaptation is NEEDED — the row reads as a clean CREATE.
- `claude-review.yml` / `claude.yml` require repo secrets (`ANTHROPIC_API_KEY` / `CLAUDE_CODE_OAUTH_TOKEN`) the scaffold cannot provision; nothing flags this at apply time.

On fleet-dashboard the fix was: add a `ci:` aggregate target (wrapping the repo's real gate) and swap setup-python for setup-node — exactly the adaptation the header asks for, but discoverable only by reading the template after the fact.

## Deliverables
- Scaffold emits a MANUAL/WARN line when it plans GH-07 and the target repo's Makefile lacks a `ci` target (it already reads files for template comparison; a `^ci:` grep is cheap).
- A one-line apply-time note on GH-08/09: "requires ANTHROPIC_API_KEY or CLAUDE_CODE_OAUTH_TOKEN repo secret".
- Optional: the ci.yml template's setup step made toolchain-neutral or clearly marked ADAPT-ME.

## Acceptance criteria
- Scaffolding a fixture repo with a Makefile lacking `ci:` produces a visible warning naming the missing target (test in tests/test_scaffold.py).
- `make ci` green; docs row in the scaffold skill's SKILL.md/reference mentions the two follow-ups.

## Dependencies & gates
- `make ci` + targets drift guard fire (skill asset + script edits regenerate targets/).
- Relates to the raptorgpt-pilot plan's findings-routing deliverable (da#33).
