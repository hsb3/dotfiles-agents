## Context

The repo's work product is **primitives** (skills/agents/hooks) authored in `primitives-core/`, tracked in the `primitives-core.yaml` roster, and assembled into `plugins/` + `.claude-plugin/marketplace.json` by `scripts/gen_marketplace.py` (`make build`), gated by `make ci`. The rules that govern authoring — edit `primitives-core/` only, regenerate (never hand-edit generated trees), the roster schema, identity-neutrality, provenance, hook layout, stdlib-only tests, branch-off-`dev`/PR-into-`dev` — currently live **only in agent-facing docs** (`CLAUDE.md`, `AGENTS.md`, `primitives-core/README.md`).

Two gaps:

1. **No human-facing `CONTRIBUTING.md`.** A contributor — or a future agent onboarding cold — has no single entry doc for the workflow and invariants. The knowledge exists but is scattered across agent digests.
2. **No skill that operationalizes creating the repo's own work product.** The marketplace ships skills for authoring *other* repos' structure (`mise-en-place-scaffold`, `repo-meta-structure`, `planning-desk`), but nothing that scaffolds/authors a new *primitive for this marketplace* to standard — a conformant roster entry, the right directory layout, passing `--check` drift guards and tests. Dogfooding gap: the repo that produces authoring skills has no authoring skill for itself.

## Deliverables

**A. `CONTRIBUTING.md`** (root or `.github/`) — distills, does not duplicate, the canonical rules (links to `CLAUDE.md` / `primitives-core/README.md` as source of truth):
- the contribution loop: branch off `dev` → edit `primitives-core/` only → `make build` → `make ci` → PR into `dev` (`main` is publish-only)
- the source-of-truth rule (generated `plugins/` / `marketplace.json` are never hand-edited)
- the roster (`primitives-core.yaml`) entry schema + `origin: authored|sourced` rule
- the invariants `make ci` enforces: roster↔disk, identity-neutrality, provenance, hook layout, stdlib-only tests
- how to run the gate locally (`make ci`, `make help`)

**B. An authoring skill** (or an extension of an existing one) for the repo's work product:
- scaffold a new primitive (skill / agent / hook) with a conformant `primitives-core/<type>/<id>/` layout + roster entry, then `make build` + `make ci` to green
- survey overlap first: `repo-meta-structure` / `mise-en-place-scaffold` cover generic repo meta-structure, not marketplace-primitive authoring — confirm the boundary before adding vs. extending
- decide whether this is one "author-a-primitive" skill or a thin "contribution-loop" skill (edit → build → ci → PR); recommend in the plan

## Acceptance criteria

- [ ] `CONTRIBUTING.md` exists, links to (does not copy) the canonical agent docs, and a newcomer can follow it to land a primitive
- [ ] The contribution loop and every `make ci` invariant are documented with the exact commands
- [ ] A decision is recorded (issue comment or ADR) on the authoring-skill shape — new skill vs. extend `mise-en-place-scaffold` / `repo-meta-structure` — with the overlap boundary stated
- [ ] If a new skill: it is rostered (`origin: authored`), builds clean, and `make ci` stays green
- [ ] `CLAUDE.md` / `AGENTS.md` gain a one-line pointer to `CONTRIBUTING.md` (no duplication)

## Notes

- The standing rule is "don't add a CONTRIBUTING file unless specifically requested" — this issue **is** that request.
- Scope is additive; no change to the generate/gate pipeline.

## Part B decision — no new rostered authoring skill; the contribution loop is served by `CONTRIBUTING.md`

**Overlap survey / boundary (confirmed).** `mise-en-place-scaffold` and `repo-meta-structure` both operate on the **generic repo skeleton** — the `_meta/` / `.claude/` / `.github/` / `docs/` taxonomy, gitignore conformance, and the `_meta/mise-en-place.yml` variance manifest that any adopted repo follows. Neither knows anything about **marketplace-primitive authoring**: the `primitives-core/<type>/<id>/` layout, the `primitives-core.yaml` roster schema, `origin: authored|sourced`, or the drift guards (`make check/build-check/identity/provenance/hook-layout/catalog`). They scaffold the *container*; primitive authoring fills the *contents* specific to this marketplace. So there is a genuine gap — but a rostered skill is the wrong vehicle to fill it.

**Why not a new rostered (shipped) skill.** `make ci`'s identity-neutrality lint (`scripts/check_identity.py`, `SCAN_ROOTS = primitives-core/{skills,agents,hooks}` + standalone READMEs) forbids any hardcoded name/org/repo/issue in a shipped body. A primitive-authoring skill is inherently repo-specific — it must name `primitives-core.yaml`, the `make` targets, the roster fields, `dev`/`main` — so it **cannot pass the identity gate** as a shipped primitive. A generic rewrite that dodged the lint would merely duplicate `mise-en-place-scaffold`. Extending either of those two skills is likewise ruled out: they are the *generic standard*, distributed to every adopting repo — injecting this marketplace's roster/build specifics would break their identity-neutrality and pollute a general-purpose standard with one repo's private tooling.

**What actually fills the gap.** The contribution loop belongs in a **repo-specific, non-shipped** doc — `CONTRIBUTING.md` (delivered in this PR at `.github/CONTRIBUTING.md`). `check_identity.py` explicitly exempts "root README, CONTRIBUTING, ADRs, _meta" (they don't ship), so it is free to name the repo, roster, and `make` targets. It documents the branch-off-`dev` → edit-`primitives-core/`-only → `make build` → `make ci` → PR loop, the roster schema + `origin` rule, and every `make ci` invariant with exact commands.

**If a dogfooding authoring skill is still wanted later**, its correct home is a **project-local** `.claude/skills/author-primitive/` — like the existing `.claude/skills/publish-to-main` (homed under the `local-dev-tooling` flow node, never distributed, never rostered, exempt from the identity/catalog gates). That is out of scope for this wave (`.claude/` is not in the wave's file ownership) and separable; recommending it be filed as its own issue rather than built here.

_Placement note: `CONTRIBUTING.md` was placed at `.github/CONTRIBUTING.md` (issue permits "root or `.github/`") — a root file would be an unhomed top-level path and fail the `make flow` guard, which would require an out-of-scope `flow.yaml` edit; `.github/` nests under the already-homed `.github` node. GitHub surfaces `.github/CONTRIBUTING.md` natively._
