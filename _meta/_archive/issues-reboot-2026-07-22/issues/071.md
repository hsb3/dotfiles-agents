## Body

Found 2026-07-04 while running the board overhaul on a real org project (mhi-raptorxai project #5), project-workflow plugin 0.2.1.

## Bug
`skills/github-project-board/scripts/*.py` share a `graphql()` helper that passes every variable with `gh api graphql -f k=v`. `-f` is always a **string** field, but the queries declare typed variables (`$n:Int!` in `PROJECT_ID_Q`, etc.), so current `gh` fails with:

```
gh: Variable $n of type Int! was provided invalid value
```

This breaks `board-export.py`, `board-apply.py`, and `board-fields.py` on first contact — the whole export→analyze→apply loop is dead until patched.

## Fix
One character in the shared helper — use `-F` (typed: coerces numbers/booleans, leaves strings alone) for variables; keep `-f` for the query text itself:

```python
def graphql(query: str, **fvars: str) -> dict:
    args = ["api", "graphql", "-f", "query=" + query]
    for k, v in fvars.items():
        args += ["-F", f"{k}={v}"]   # was -f
```

Verified: with this patch all three scripts ran clean against the org project (92-item export, 384-row changeset applied, idempotent re-run 0 changed).

## Two adjacent paper cuts from the same session (fold in or split, your call)
1. **Changeset header row:** `board-apply.py` requires the `issue<TAB>field<TAB>value` header (documented in the docstring) and silently plans `0 changed · 0 unchanged · 0 skipped` on a headerless file — a headerless TSV looks like a successful no-op. Consider exiting non-zero when zero rows parse, and/or telling the board-analyst agent prompt to always emit the header (the bundled analyst produced headerless TSVs).
2. **`--owner-type` default is `user`:** on an org project the failure surfaces as the (misleading) Int! error above rather than "project not found". After the -F fix the error becomes the proper `project not found (check --owner-type)` message, so this mostly resolves itself — noting for test coverage.
